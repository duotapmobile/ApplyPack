Independent review identified that process death could leave sensitive S3 temporary objects without a durable deletion obligation. A separate `ap_aws_temporary_cleanup` table prevents an old maintenance process from treating AWS object keys as Supabase Storage paths. Existing `storage_cleanup_queue`, its bucket/path rules, artifact-registration triggers, retry behavior and published migrations remain unchanged.

Service-only `ap_begin_aws_temporary_cleanup(p_operation_id uuid,p_deployment_environment text)` atomically stores four exact paths under `ephemeral/<lowercase UUIDv4>`: the base source, `.render.pdf`, `.page-1.png` and `.page-2.png`. It binds the exact account/environment bucket and canonical commerce origin. Its JSON result is `{operationId,createdAt,notBefore,submissionDeadline,bucket,keys,completed}`. The cleanup delay is ten minutes from the stored database creation time; the submission deadline is sixty seconds from that same time. Replays return the original identities and times. Cross-environment or incomplete groups fail; any completed row makes `completed` true so runtime can reject reuse.

Completed rows retain non-sensitive operation metadata. Service access is SELECT plus updates only to attempts, sanitized error/attempt time and completion time; insert is through the RPC and delete is denied. A trigger preserves identity/lease fields and monotonic attempts/completion. Pending and dead-letter maintenance queries must exclude completed rows. Runtime must register before both upload and invocation, enforce the short submission deadline, delete only exact registered keys through the correct AWS environment, and retain unacknowledged deletion obligations. Runtime implementation and provider validation are separate from this SQL report.
