## Concrete proposed scope

The authorized local implementation is a separate retention job, intended for a five-minute schedule after separate hosted approval, limited to:

- AWS account `838445019912`, region `us-east-1`, bucket `applypack-production-protected-recovery-838445019912`.
- A dedicated role `arn:aws:iam::838445019912:role/applypack/production/applypack-production-recovery-retention`, with its own short-lived Roles Anywhere leaf and profile. It cannot reuse the web or backup writer identity.
- Listing exact object versions only under `objects/` and `manifests/`. No private document reads, document writes, database credential, or changes to the primary source storage.
- Removing an exact archived object version only when two fresh, complete, matching source inventories and verified historical manifest references establish its identity and an applicable expiry or explicit deletion basis, with no active paid obligation or legal hold requiring it. Absence from the current inventory alone is insufficient. Any malformed, stale, incomplete, conflicting, or changed inventory stops the run.
- Preserving versions uploaded after the first inventory began, protecting uploads that are still being registered or backed up.
- Removing exact manifest versions more than seven days old only after verifying a usable replacement checkpoint and its required object references remain. Current private-file versions remain subject to their source retention policy, rather than a seven-day file-deletion rule.
- Verifying the selected versions are absent after removal and recording a separate retention heartbeat. A failed or unverified operation must not refresh that heartbeat. Failure and staleness alerts remain required.

Deletion of an archived S3 object version is irreversible through this archive. The current proposal does not authorize deleting primary customer files, modifying payment/history records, or deleting currently retained backup versions.

Its output explicitly says `READ_ONLY_NOT_AUTHORIZED_TO_DELETE` and `providerMutationPerformed: false`; stdout contains only fixed statuses, source release, report digest and counts. The detailed in-memory report records retained versions, source inventory digest and target bucket. Every private object and manifest version is preserved, and `proposedRemovals` is empty. Manifests older than seven days remain informational candidates only. The planner contains no deletion command, write command, or completion-heartbeat submission.

Read-only historical mapping is implemented and does not require deletion authorization. Optionally supply `--manifest-evidence <private-json-file>` containing an array of existing `{digest, versionId, manifest}` records. The file is limited to 64 MiB and is private metadata, not a place for credentials or customer document contents. The mapper reuses the existing manifest schema/digest checks, binds exact listed manifest and object versions/sizes, records all historical reference retention and latest deletion/revocation restrictions, and rejects conflicting immutable-version claims. Null retention remains unbounded or held; a removed or replaced reference is not permission to erase its old bytes. Unmapped versions and missing historical manifests remain unresolved and preserved.

The detailed in-memory report includes private storage paths and reference identifiers. The CLI does not serialize that graph, names, paths or identifiers to stdout and does not write a private report file. An authorized programmatic caller must keep that detailed result private and outside routine logs or chat. Imported metadata stays in memory and is never sent to a provider. Current null retention and newly added shared references are also treated conservatively, even when the historical reference had a finite deadline.

A replacement receives `METADATA_VERIFIED_ONLY` only when the supplied history covers every listed manifest version and a fresh checkpoint matches the current release and complete source graph, has no current retention conflict, and has every exact referenced archive version in the listing. Imported metadata and listing consistency do not authenticate provider bytes, prove checksum/decryption integrity, establish an application completion receipt, or prove a usable hosted restore. The report explicitly marks all those hosted proofs unverified. The retention identity gains no manifest/blob read permission; an independently authorized operator supplies existing manifest exports. Without imports the command remains a listing-only report. Local executor implementation and fictional-data testing are authorized; actual operation and retention acceptance still require approved resources, verified provider identities, independent review, hosted verification and explicit hosted deletion approval. Hosted proof is not a prerequisite to writing the authorized code.

The planner rejects unexpected delete markers, duplicate versions, pagination loops, invalid keys, wrong accounts, stale source inventories, and unbounded reads. It accepts only the dedicated retention capability, which cannot download source documents or submit a backup completion.

Local offline tests cover preserving current, expired, revoked, missing, superseded, and held file versions; shared historical paid references; seven-day manifests; incomplete imported history; conflicting versions/hashes; absent exact blob versions; stale/wrong-release replacement metadata; in-progress uploads; authorization separation; complete pagination; failures; and hard deadlines. ## Separate local executor and durable proof

`node scripts/run-protected-recovery-retention.mjs` is the separately implemented exact-version executor. Both `APP_ARCHIVE_LIFECYCLE_ENABLED` and `APP_ARCHIVE_RETENTION_EXECUTION_ENABLED` must be true, and all hosted gates below must first be satisfied. Configuration remains default-disabled. The executable accepts no alternate target, URL, prefix or plan file. It uses the dedicated retention identity and sends only its fixed capability to `/api/internal/archive-lifecycle`. It cannot read private archive bytes or delete anything under `database/`.

The trusted server uses a separate short-lived [read-only verifier identity](../../infra/aws/archive-verifier/README.md). It authenticates canonical bytes of every historical manifest and exact referenced version metadata, checks the current acknowledged application checkpoint, and recomputes the plan from two complete source inventories. Imported evidence and a caller's verification digest never substitute for these reads. Finite historical schema support preserves original bytes; unknown schemas, incomplete history, delete markers, conflicting claims and read caps block the whole operation.

Migration098 supplies a durable maintenance fence. It covers registered private ownership and file-alias tables, paid/checkout/refund/hold/restore dependencies and actual private Storage object/bucket mutations, and pins the transitive ownership/retention helper definitions. A changed graph or function body fails coverage. Relevant writes return a retryable error; ordinary unrelated account/support activity is not blanket-blocked. Verified webhook/provider-event intake remains durable, and unapplied events block begin and each new delete dispatch. Both archive writers register before source/provider work. Legacy writer revisions and credentials must be retired before activation because old S3 writers cannot be fenced by a new database row.

Each planned version gets one durable dispatch record before one exact S3 DeleteObject VersionId request. Eligible manifests are deleted before their object bytes. A lost response leaves the operation uncertain and the fence held. The explicit command `node scripts/run-protected-recovery-retention.mjs --reconcile <run-uuid>` never creates a delete client or redispatches; it asks the server to observe exact absence and reconcile stored state. A still-present uncertain version stays locked for operator investigation. A safe cancellation retains unstarted versions, and bytes orphaned by partial cancellation remain preserved. The implementation does not infer a new deletion basis for those orphan bytes.

Only independently observed absence for every planned version, a still-current matching file checkpoint and fresh complete remaining archive proof can create a successful immutable receipt. The server stores that receipt and `protected_recovery_retention` heartbeat atomically using the original run-start watermark. Cancel, timeout, unconfirmed result or repeat receipt does not refresh success. The old worker-asserted `/api/internal/protected-recovery/retention-complete` endpoint now returns authenticated409 and leaves historical evidence unchanged.

There is no automatic fence expiry. Before any operational recovery of an uncertain run, reconcile exact writer/deletion state and current payment/hold obligations; never clear a fence or recreate a plan to evade that requirement. The separate file/database/retention proofs are all required for readiness, with ten-minute warning and twelve-minute intake/checkout hold against the fifteen-minute target. Actual provider access, lifecycle races, schedules, alert delivery, independent restore and runtime retirement remain unverified hosted acceptance items.

## Separate hosted-operation gate

“I authorize implementing and running the separate five-minute backup retention job described here, including irreversible removal of only the exact obsolete or expired archive versions it verifies in the specified bucket. Keep primary files, currently retained backup versions, and payment records unchanged.”

The local implementation approval does not supply this hosted-operation authorization. Provisioning paid resources still requires the consolidated cost approval, and production launch still requires hosted verification, human acceptance, and the final go-live decision. The `database/` prefix is outside this deletion scope: every retained database manifest pins its exact file manifest and object versions. Unknown, malformed or incomplete database history blocks pruning. Consequently this scope alone cannot establish bounded long-term database archive growth or a fixed storage quote.
