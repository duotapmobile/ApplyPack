The observer runs in AWS, outside Railway, once per minute. It reads only `/api/internal/operations-monitor` from the fixed production and staging origins. It never runs maintenance, accesses customer content, invokes a document worker, reads private archives, decrypts application data, or sends customer messages. The service response is a fixed set of coarse status/age values with the exact deployment identity and a fresh request nonce. Failed authentication, a different release or database, stale evidence, DNS/TLS/HTTP failures, redirects and malformed responses all produce unhealthy metrics. A missing observer metric also causes an alarm.

Production has four checks: completed maintenance, private-file recovery, authenticated database recovery completion, and protected archive retention. Staging has completed maintenance. Recovery warnings begin when the source watermark reaches ten minutes; recent upload or verification time cannot substitute for that watermark. The database check requires the immutable, independently verified completion record introduced by098. A missing record or old schema is UNKNOWN. It does not extend or certify recovery coverage. The production checkout/intake guard requires all three file, database and retention checkpoints for the exact current release and database schema; it stops new acceptance at twelve minutes and fails closed when a checkpoint is missing, malformed or unavailable. The guard and observer share the database assessment. Existing paid obligations and authenticated access to an existing intake draft remain available. The observer does not unlock checkout or intake.

Maintenance is healthy only after verified completion for the current release and environment, with no unresolved condition. It becomes stale after twenty minutes: the fifteen-minute schedule plus a five-minute execution budget. An active diagnosis is RUNNING, not completed success. Five consecutive one-minute unhealthy/missing maintenance points trigger its alarm, allowing a bounded normal run to finish. Recovery alarms use two consecutive points. These are warning/alert targets, not guarantees of delivery time or a measured recovery-point objective. A stop of the observer itself is detected by missing data. CloudWatch and SNS are still dependencies; actual receipt must be tested.

The schedule invokes an immutable numbered Lambda version whose published code must match the package receipt's base64 SHA-256. The version description also binds both expected application release SHAs so a release-configuration change publishes a new version. Both EventBridge delivery and Lambda asynchronous handling have zero configured retries and a sixty-second event-age limit; the schedule depends on that invocation policy. AWS SDK calls have one total attempt. These bounds avoid Lambda's default two error retries and six-hour queue; they do not guarantee exactly-once invocation or a hard spending cap. Missing-data alarms remain the response to failed observation.

A separate `applypack-worker-bucket-monitor` function reads only the versioning state and policy of the two fixed temporary document buckets every five minutes. It uses an independent role with no object, KMS, SSM or application access. Both buckets must be never-versioned and retain the exact unconditional policy denying versioning changes. Suspended versioning, conditional or missing denial, wrong owner, malformed evidence and provider failure are unhealthy. Every request includes the expected bucket owner. The aggregate `DocumentWorkerBucketsHealthy` metric has no names, object keys or policy content; missing evidence alarms after two five-minute periods. This detects configuration drift and does not prove historical object absence or perform cleanup. The application worker's own preflight and cleanup controls remain required.

Two additional alarms observe `AWS/Lambda` `Errors` on the exact staging/production document-worker function names. One observed error alarms; missing data is non-breaching because an idle worker has no invocation to report. These alarms do not prove that a worker can be invoked or that its permissions/network isolation are correct. The bucket observer uses a separately hashed immutable code version, activation-bound version description, thirty-second runtime limit and zero-retry/sixty-second-age delivery configuration. Its twelve injected-client checks passed. ## Cost inputs and remaining scope

This design uses two128MB Lambdas bounded at45/30seconds, one one-minute and one five-minute EventBridge rule, six custom CloudWatch metric series, eight metric alarms, one shared SNS topic/subscription, two seven-day log groups and two Standard SecureString parameters under an existing key. It reuses an existing versioned code bucket. Budget actual Lambda duration, requests, bucket-control reads, parameter/KMS requests, metrics/alarms, logs and SNS delivery together in the consolidated quote. No free-tier allowance is assumed. This is the concrete replacement for the earlier six-metric/eight-alarm planning reserve; do not add that reserve a second time. Nothing here is provisioned or accepted.

Alarms notify; they do not delete data, change checkout, deploy a revision, repair an archive or run an application job. Follow locked forward recovery: stop new intake/checkout when required, preserve paid obligations, investigate the fixed failing check, repair forward and prove fresh evidence before reopening.
