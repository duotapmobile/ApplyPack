# Automatic research preparation

This component prepares research from the exact customer-confirmed intake. It does not approve a job, invite payment, or deliver a search automatically.

The environment switch `APP_AUTOMATIC_RESEARCH_ENABLED` and the singleton database preparation configuration both default to disabled. Applying migration100 creates the queue and its authorization checks; it does not activate collection or purchase access. The existing job-source collector and feasibility worker retain their separate configuration and permissions.

Before enabling this component in an environment, verify the deployed revision and schema, the exact approved source authorization and current authorization head, the enabled source schedule, and the approved feasibility source configuration. Enumeration permission does not establish permission to display jobs in a paid service. Do not enable a source merely because its API is publicly accessible. Use the existing approved-source process and preserve its documentary evidence, host restrictions, bounds, quotas, and lease checks.

The database configuration accepts the exact reviewed configuration IDs through `ap_configure_research_preparation`. It requires a current operator or administrator and the expected configuration version. Configure only the IDs reviewed for that environment. Enabling the environment switch alone cannot bypass this configuration.

On maintenance, one bounded preparation is advanced. Its plan is derived from the confirmed snapshot and its source configurations. The existing collector performs the permitted requests. Preparation binds a successful complete capture to the exact source run and authority. Stale, failed, partial, or unavailable captures cannot establish completed coverage. Unknown responses are held for reconciliation rather than blindly retried as completed work.

In the matching workbench, the operator opens the prepared research and checks the captured official listing and application link. Each source verification requires actual employer identity, active-listing, application-path, and legitimacy checks. This records reviewed evidence; it is not a provider attestation. The operator then records exact candidate-to-requirement evidence and usefulness reviews through the existing controls. Evaluation derives results from those records. It does not accept invented gate results or scores from the browser.

Coverage can be completed only after every admitted observation has a current evaluation. A complete empty source capture still requires explicit owner coverage review. Unsupported or ambiguous requirement text is shown as a parser hold. It must remain unresolved until a permitted, independently supported source or existing reviewed workflow resolves it. Do not mark a capture complete, manufacture criteria, or loosen eligibility to clear this hold.

Feasibility waits for the preparation and coverage evidence. Ten preliminarily deliverable, distinct reviewed opportunities are required before the separate owner invitation action. An insufficient result remains limited and must not invite payment. Existing capacity, expiry, and checkout authorization remain in force.

A superseding confirmed intake invalidates the old snapshot's authority and enqueues its own preparation. The separate clarification-confirmation migration supplies renewed full review; migration100 alone does not implement that customer workflow. Historical snapshots, observations, reviews, and paid obligations are retained under their existing policy. Purged or pending-purge metadata shells cannot consume the bounded queue ahead of valid work.

Validation must distinguish three states: local route/database proof using fictional source transport, actual hosted provider/source proof, and live customer operation. The local test harness does not establish provider permission, hosted Supabase behavior, real job availability, or launch readiness. Keep checkout locked until the release acceptance evidence and final owner approval are complete.
