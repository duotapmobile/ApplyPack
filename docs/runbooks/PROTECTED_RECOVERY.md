## Scope and recovery promise

The agreed loss scenario is loss of the original machine or its credentials. The target is recovery within 240 minutes and at most 15 minutes of recent application data requiring recovery or reconciliation. Stripe remains the independent payment ledger: reconcile every paid transaction before opening customer access. Protected database recovery, private object recovery, envelope-key custody, authentication, and configuration are separate dependencies. An object checkpoint alone proves neither database recovery nor a complete service restore.

The prepared database design is the separate, bounded snapshot-export worker described in [Database recovery worker](DATABASE_RECOVERY_WORKER.md), paired with an exact acknowledged file checkpoint. Evaluate it against the agreed recovery targets in the consolidated quote and hosted drill. Supabase PITR is an alternative or additional paid resource only if selected and approved; it is not an automatic mandatory purchase. Neither PITR nor a database dump includes Storage object bytes. A daily dump alone cannot satisfy a fifteen-minute recovery point. Do not expand the tested loss scenario into a promise against total provider-account or project destruction.

## Copy and publication

The copy service streams each retained source version into the durable bucket using the exact KMS key. Archive object keys are derived from source bucket, key and immutable provider version; the manifest binds original identity, byte length, SHA-256 and exact S3 VersionId. An S3 version acknowledgment and stored checksum must match the streamed bytes. An ETag is not a SHA-256 checksum.

Existing matching versions can be reused from a verified prior manifest. Lost upload responses may leave an unreferenced version; they cannot publish partial success. After copying, obtain a second complete source scan with an identical digest. Publish the immutable manifest last, then report completion. The writer may read manifests but cannot read archived customer blobs, delete archive versions, or change IAM or KMS policies.

`operational_heartbeats` records task `protected_recovery`. Its `last_succeeded_at` is the first scan's source-start time, never the finish time. Its versioned summary binds exact project/release, source start, completion, inventory digest, manifest digest/VersionId and counts. A conditional monotonic update rejects repeated and older completions, including concurrent races. Receipt HMACs authenticate the application source scan; they are not AWS or Supabase attestations. The completion caller is a trusted publisher whose actual upload behavior must pass hosted verification.

The application requires all three proofs: current file checkpoint, authenticated database COMPLETE receipt and verified retention completion. Missing evidence, a wrong project/release/schema, or failed independent validation cannot show green. It warns at ten minutes and stops new production intake and checkout at twelve minutes of source-watermark age, leaving margin before the fifteen-minute target. This readiness hold does not erase paid obligations. During a separate active archive-maintenance fence, relevant writes receive a retryable error as described below; verified webhook intake remains durable. Deliver failure and staleness alerts through an independently functioning notification path; configuration and unit tests are not delivery proof.

It cannot read customer archive bytes, write them, decrypt them, or use writer capabilities. No blanket S3 expiration is configured. Unknown/null versions and delete markers fail closed; the current executor does not infer an erasure basis for them. The `database/` prefix is never a deletion target.

The local executor compares two complete fresh source inventories under a durable database fence, authenticates historical manifest bytes with a separate read-only provider identity, and maps every retained database archive to its exact file manifest and object versions. It deletes eligible manifests before their now-unreferenced bytes so a partial cancellation cannot leave a retained manifest pointing at deleted data.
